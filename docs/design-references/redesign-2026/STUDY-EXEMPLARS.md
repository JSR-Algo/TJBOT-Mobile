**Principles**
- Information architecture: Fixed top status bar (hearts, fire/streak, XP, gems) → Primary lesson hero card (60-70% of fold, progress bar, centered) → One reward alert (yellow/gold, countdown timer) → Module grid below (2-3 columns, 80-120px thumbnails). No competing hero cards; lesson is the clear visual entry point.
- Visual hierarchy by size and color: Lesson card 1.5-2x module card size. Gold/yellow reserved for rewards and streaks (warm emotional value). Purple/blue for primary CTAs. Pink/orange for mascot variety. Minimum 16px gutters between cards create breathing room and reduce cognitive load for young learners.
- Daily lesson as large tappable card, not a list row: Unit/day title + progress bar (e.g., '15/30 words learned') + optional gold badge + optional mascot thumbnail. Card is padded and shadow-elevated; tap opens lesson or preview. Tactile, discoverable entry point.
- Streak visibility and celebration: Day streak in dedicated micro-card (e.g., purple circle with '1'). Show both current ('1 day') and personal best ('Longest: 5 days') for psychological reinforcement. Include daily stats ('15 words reviewed', '9 new words', '26 min learning') in sub-card. Prominent on home, never buried.
- Mascot as emotional anchor: Mascots in diorama scenes (shelves, rooms) not floating. 30-40% of home screen, center-right or center position. Simple, cheerful, wordless facial expressions. Seasonal variants (summer, holiday mascot) signal limited-time engagement. Owl + companion character create partnership narrative.
- Primary CTA treatment: Warm button colors (yellow/orange for 'Start Lesson', blue for secondary). Pill-shaped or rounded-rectangle, full-width or 80% width, above fold or inline with lesson card. Action-oriented labels ('Continue learning', 'Start Unit 1', 'Practice now'). Secondary CTAs (muted color, half-sized) placed below primary.
- Content density and scroll trigger: First fold shows status bar + lesson hero + one reward alert + 2-3 module thumbnails; total 500-600px on iPhone. No hidden onboarding; lesson and streak immediately visible. Density increases below fold. No 'swipe to see more' on first view.
- Color palette for kids: Gold/yellow for rewards, achievements, mascots. Blue/purple for CTA buttons and badges. Light gray/white backgrounds, dark gray body text. Pink, light green, teal for module card variety (no adjacent cards same color). WCAG AA contrast minimum (4.5:1 body, 3:1 large text).
- Feedback and motion: Lesson card has subtle shadow increasing on press (haptic signaled visually). Progress bar animates on lesson completion (fill in 300ms, 'pop' effect). Streak badge scales on unlock (bounce, 200ms). No flashing patterns; reduced-motion mode disables all animation.
- Navigation consistency: Bottom tab bar with 5-6 icons (home left-most, lessons, profile, explore, etc.). Home is root view; no back button on home. Tab bar remains visible during lesson selection, hides during gameplay. Top bar shows status + optional menu (three dots), never back button on home.
- Lesson progress granularity (multi-unit model): If lessons grouped by unit (Lesson 1, Lesson 2, ... Lesson 50), show current unit as hero card; list next 3-5 lessons below in compact grid. If grouped by topic (Greetings, Numbers, Colors), show current topic as hero; modules as 2-3 column grid. Progress bar always shows units completed (e.g., 'Unit 3 of 50') to avoid false completion psychology.
- Parent lane differentiation: Parent/guardian view shifts to operational metrics (child's streak, lessons completed this week, time spent, next steps). Muted color palette (blues, greens, whites); mascots smaller or absent. Top tabs (Overview, Activity, Settings) instead of bottom tabs. Factual summaries ('Emma completed 5 lessons this week'), no gamified alerts.
- Accessibility beyond color: Icons paired with text labels on home (no orphan icons). Tap targets 44x44px minimum (buttons), 48x48px (nav tabs). Text color verified with WCAG Contrast Checker. System font scaling to 200% without layout collapse. VoiceOver/TalkBack describe status ('Day streak: 1 day', 'Unit 1, progress 1 of 51').
- Reward and streak psychology: Visible counter for consecutive days ('Day 5 of 7'), not just 'active today'. Milestone badges at days 3, 7, 14, 30 unlocked with visual fanfare (confetti, gold glow, pop sound). 'Next reward in X hours' notification prevents end-of-day cliff; creates re-engagement loop. Optional leaderboard or friends' stats in small card (social proof without pressure).
- Module state clarity: Locked modules gray out; current unit has border or highlight ring. Unlocked modules are color-coded (purple, blue, pink). Premium modules have badge or lock icon. State distinction through color alone allows children to understand accessibility without reading; text confirms for parents and accessibility tools.

**Anti-patterns**
- Flat card grids with uniform spacing and no hierarchy: Every lesson card same size, same color, same shadow. Children cannot distinguish between 'try this next' and 'locked, come back later'. Use scale, color, and state indicators instead.
- Mascot floating or oversized: Mascot takes 60%+ of screen or floats mid-screen without anchoring. Reduces space for lesson content and breaks the narrative (mascot feels intrusive, not supportive). Keep mascot 30-40%, in a diorama or scene.
- Lesson entry as a list row: Lesson appears as a thin row in a scrollable list (e.g., 'Lesson 1  [progress bar]'). Children cannot easily tap; no visual affordance of interactivity. Use large cards instead.
- Hidden streak or progress: Streak buried in a 'Stats' tab or profile view. Children forget to maintain streak because they never see it on home. Make streak visible on first load.
- Reward countdown without urgency cue: 'Next reward available: 11 hours' shown statically without a timer or visual urgency. Child loses motivation. Use countdown animation or color shift as timer approaches zero.
- Color-coding alone for accessibility: Locked, unlocked, premium states only differ by color. Colorblind children cannot distinguish. Always pair with text labels, icons, or outline patterns.
- Bottom navigation with too many tabs: 7+ tabs clutter the navigation bar. Children tap wrong tab repeatedly. Keep to 5-6 maximum; group related features.
- CTA button same color as secondary elements: Primary 'Start Lesson' button same blue as module card backgrounds. No visual priority. Use warm (yellow/orange) for primary; cool (blue/purple, muted) for secondary.
- Scroll required to see lesson of the day: First fold shows only status bar + mascot, no lesson card until scroll. Children may not find the lesson. Lesson hero must be visible at first load.
- No state feedback on tap: Lesson card shows no visual response (shadow, scale, color shift) when tapped. Child unsure if tap was registered. Add subtle shadow, scale, or highlight on press.
- Streak reset without warning: Streak counter resets at midnight silently; child doesn't realize they missed a day until checking. Notify child in advance if at-risk (e.g., 'Complete 1 more lesson today to keep your 5-day streak').
- Language-specific coin/gem economy unrelated to learning: Gems require real-money purchases or excessive grinding with no relationship to lesson completion. Feels extractive. Tie all rewards directly to learning progress; premium features optional, not required.
- Too much text on home: Buttons with 3+ word labels, explanatory prose, tips, notifications all competing. Cognitive overload for young learners. Use single-word or 2-word labels; move explanations to tutorials.
- No empty state guidance: If no lessons available (new account, all lessons locked), screen is blank or shows only mascot. Child confused; doesn't know what to do next. Show 'Complete Lesson 1 to unlock Lesson 2' with a CTA to start.
- Reduced-motion mode ignored: Animation-heavy design with no system-level reduced-motion support. Children with vestibular disorders experience discomfort. Check 'prefers-reduced-motion' and disable all animation.
- Module unlock logic unclear: Child taps a locked module; nothing happens or a vague error appears ('Not available'). No guidance on how to unlock. Show 'Complete Lesson 5 first' with a CTA to that lesson.
- Streaks without meaningful incentive: Day counter increments but offers no gameplay reward (no badge, no milestone, no social recognition). Child sees streak as decoration; drops it easily. Celebrate at 3, 7, 14, 30-day marks with tangible unlocks.
- Parent/child lane design indistinguishable: Both lanes have same visual language, same mascot, same gamification. Parent cannot quickly switch context. Use distinct color schemes, typography, and information density.
- Notification fatigue: Reward alerts, milestone unlocks, friend requests, seasonal events all show at once on home. Child ignores all. Prioritize: only show 1 alert per session; queue others in a notification center.
- Lesson card progress bar not descriptive: Progress bar filled 30% with no label ('15/50' or 'Unit 3 of 10'). Child unsure what '30%' means (30% done? 30% of unit? 30% toward reward?). Always label with completed/total count.

**Principles**
- Character as Scene Anchor: Position the character (animated mascot, speaking avatar, or contextual figure) prominently to create emotional connection and signal that this is a speaking lesson. Character can be placed center-stage for feedback/encouragement, or left/right for dialogue screens. Character expression should change with lesson outcome (happy for success, supportive for struggle). For TJBot CHILD lane: keep character playful and expressive (Garden Blue storybook aesthetic); for PARENT lane (Wispr-Flow): use a calm, professional companion character.
- Information Architecture—Zenlike Simplicity: Every lesson screen shows exactly three elements: (1) instruction/task, (2) content card (word, picture, dialogue), (3) primary action button. No more. Navigation, hints, and secondary actions are placed below the fold or in minimized form (help icon, video link) so they don't compete for attention. Text instructions are one sentence, 8-12 words max. Duolingo and Khan Academy both follow this strict hierarchy.
- Audio as Central Interactive Element: Audio playback is surfaced via a speaker icon or 'Listen to dialogue' button, never auto-playing. Each speaking character gets a distinct audio icon or play button adjacent to their line. For multi-character dialogue, use left/right positioning + speaker icon to clarify who is speaking. Audio is essential—never treat text as the only input. TJBot CHILD lane should use colorful, large audio buttons (easy for small fingers); PARENT lane can use subtle speaker icons.
- Visual Hierarchy—Primary Action Dominates: The CONTINUE button is always the largest, most saturated element on the screen (typically 48-56pt height, full width or near-full width, centered at bottom of visible area). Button color is the brand accent (Duolingo green, Babbel orange, Speak cyan). Button text is always a simple verb: CONTINUE, CHECK, NEXT, or LET'S GO. Secondary actions (hints, video, replay audio) are 25-30% smaller and use muted colors or outline styles. This visual dominance ensures users always know what to do next.
- Responsive Touch Targets: All interactive elements (audio icons, answer options, buttons) must be ≥44pt diameter for children's apps (accessibility + dexterity). Primary button should be 56-64pt height. Audio icons should be 40-48pt and have clear hover/tap states. Card images should be tappable (if selectable) and show a clear border highlight on selection. Khan Academy's picture grids use 12-16pt borders and clear focus states—ideal for child interaction.
- Content Density—Whitespace as Feature: Screens deliberately use generous vertical whitespace (2-3x normal margins) to reduce cognitive load and focus attention. No scrolling on a single lesson step—everything fits above the fold (except the primary button, which sits in the safe zone at bottom). This creates breathing room for the character and cards to feel prominent. Use monochromatic or very muted backgrounds (light gray, white, off-white) to avoid visual noise.
- Progress Indicators at Top: Show lesson step visually (progress bar or dot carousel at the very top of the screen) so users always know where they are in the lesson sequence. Use a thin, low-contrast bar (often tinted in the app's secondary color) that occupies <10% of vertical space. Do not use percentage text ('Step 5 of 12')—just show visual progress. This satisfies both parent (operational awareness) and child (gamification signal) needs.
- Picture/Word Cards as Focal Points: If the lesson is word + picture, the card should be 180-240pt wide, centered horizontally, and positioned in the upper-middle area (leaving room for instruction above, button below). Use a subtle border or drop shadow to make the card feel like a physical object to interact with. High-contrast, colorful illustrations (Khan Academy's animated animals, Duolingo's narrative scenes) make cards feel alive. Never use dim or stock-photo style images—cards should feel hand-crafted and delightful.
- Character Expression & Microinteraction: Character should have 2-3 distinct states: (1) neutral/ready, (2) speaking (mouth animates, eyes may focus forward or downward to show concentration), (3) reacting to user action (smile/thumbs-up on success, encouraging shrug on struggle, neutral on neutral). Use Lottie or Rive animations for smooth eye blinks, mouth movements, and small gesture loops (wave, nod). For TJBot robot: leverage the physical screen on the device to show synchronized facial animation—this creates presence and engagement.
- Dialogue Cards Use Speaker Icons Not Names: When showing conversation, place a small avatar (16-20pt circle) or icon to the left or right of each line, paired with a speaker icon. Avoid cluttering with speaker names (e.g., 'User:' / 'Teacher:'). Icon positioning (left vs. right) can implicitly show who's speaking. Audio icon should appear inline with the text, not in a separate column. This keeps dialogue scannable and reduces visual complexity.
- Color Coding for Feedback & State: Use consistent, app-wide colors for feedback: green (✓ correct, success), orange (! attention, hint), red (✗ incorrect), blue (ℹ info, help). Backgrounds should be 95%+ white or very pale (near-white). Apply color only to buttons, badges, feedback boxes, and character accents—never color the entire screen. This ensures the child's eye travels predictably: instruction → card → button.
- Feedback Latency & Celebration: After user action (button tap, picture selection, audio response), show immediate visual feedback (1-2 frame animation, micro-interaction) within 100ms. If the answer is correct, display a celebration tone: upbeat character reaction, optional confetti or sparkle animation, positive text (e.g., 'Nice job!' not 'Correct'). If incorrect, show a supportive tone: character nod with gentle message (e.g., 'Let's try again' not 'Wrong'). Never use shame language. Lesson-complete screens should feature full celebration (colors, confetti, achievement badges) with the character as the emotional anchor.
- Typography Hierarchy: Instruction text should be 16-18pt (or font-size: 1rem, line-height: 1.5), dark gray or black, left-aligned. Character dialogue or feedback should be 18-20pt, color-coded by speaker or intent. Button text should be 16-18pt, sans-serif, bold (600+ weight), all-caps (e.g., 'CONTINUE', 'CHECK'). Avoid serif fonts except for display/logo use. Use max 2 font families per app (body sans-serif + heading sans-serif with different weight).
- Safe Zone & Gesture Conflicts: Position the primary button at the bottom center, with ≥16pt padding from the bottom edge (iOS/Android safe area). Ensure the button does not conflict with system gestures (swipe-to-go-back, bottom swipe on Android). If the lesson requires dragging (e.g., Khan Academy's manipulatives), place drag targets in the middle-to-upper area and keep the bottom 80pt as gesture-safe for the CONTINUE button. For TJBot, test that tap-to-continue does not accidentally trigger system navigation.
- Accessibility Contrast & Mobile-First Sizing: All text must have ≥4.5:1 contrast ratio against background (WCAG AA minimum; 7:1 preferred). Interactive elements (buttons, icons, cards) should have ≥3:1. Test text rendering on small screens (5.5-6.5 inches) at arm's length to ensure readability for both children and parents. Use system font sizes or relative units (rem) so OS-level text scaling is honored.
- Parent-Lane Subtle Indicators: In the PARENT lane (Wispr-Flow operational context), add discrete progress metadata at the top or via pull-down (lesson name, topic, estimated duration, progress %). Use a calm color palette (blues, teals, soft grays) instead of primary colors. Character can be a professional avatar rather than a playful mascot. Feedback language should be operationally clear: 'Your child just learned 5 new words' rather than celebratory tone.

**Anti-patterns**
- Auto-playing audio on screen load: Forces the child (or parent) to scramble to pause. Always require a tap on the speaker icon to play—respects user control and pace of learning.
- Multiple buttons visible simultaneously: If a user sees CONTINUE, SKIP, HELP, and REPEAT buttons, they experience choice paralysis and don't know which is primary. Show only CONTINUE (and maybe HELP as a small icon); hide SKIP/REPEAT behind a long-press or settings menu.
- Unclear speaker in dialogue: When two characters speak without clear visual differentiation (no avatar, no position change, no color), children get confused about who is saying what. Duolingo's avatar-on-left/right pattern is proven; always use it.
- Text-only instructions: 'Read the sentence and choose the correct picture.' Children (and many adults) learn better with spoken instruction. Pair all text instructions with a character audio voiceover that reads the instruction aloud. This creates dual-coding (text + audio) and shows that this is a speaking lesson.
- Scrolling lesson content: If a lesson screen requires scrolling to see the answer options or button, users get lost. Everything must fit above the fold. If content doesn't fit, split it across multiple screens instead of scrolling.
- Harsh error messages: 'Wrong. Try again.' feels punitive. Instead: 'Good try! Listen again and repeat.' Children are still learning; feedback should be encouraging, not judgmental.
- Character hidden or off-screen: If the character is a tiny icon in the corner or absent from the feedback screen, the emotional connection dissolves. The character should be visible, expressive, and react to user action. This is non-negotiable for a robot companion app like TJBot.
- Low-contrast or busy backgrounds: Gradients, patterns, or photographic backgrounds compete for attention and make text hard to read. Keep backgrounds simple (white or 95% opacity gray) so the character and card content stand out.
- Progress bar that resets or misaligns: If the progress bar at the top resets unexpectedly or shows a different count than the actual step, users lose trust in the lesson sequence. Always keep it in sync with the current step, never hidden.
- Small or unclear audio icons: If the speaker icon is <32pt or monochromatic gray, children miss it and don't realize they can tap to hear the word/dialogue. Make audio icons bright (brand color), 40-48pt, and always visible next to the relevant content.
- Celebration only on perfect score: If the app only celebrates when the user gets 100% correct, it discourages struggle and exploration. Instead, celebrate effort and progress ('You tried 3 times—great persistence!'), not just perfection.
- Character expressions that don't match the lesson outcome: If the character smiles when the user got the answer wrong, or looks sad during a celebration, the emotional signal is broken. Sync character animation to lesson result explicitly.
- No touch feedback on buttons: If a button doesn't change appearance (color, shadow, scale) when tapped, users doubt whether their tap registered. Use a 50-100ms scale-down and color shift to confirm interaction.
- Inline ads or CTAs within lesson flow: Even 'soft' CTAs ('upgrade to unlock more!') interrupt the learning moment. Keep lesson screens clean and ad-free; only show engagement offers after a lesson completes.

- Child profile customization with visual choice: Avatar/character selection screen with 9–15 options in grid layout. Seeing own choice builds ownership and engagement. Emoji or illustrated characters, not abstract icons.

Color palette: primary (vibrant green/magenta), secondary (warm orange/yellow accent), neutral (calm white/light gray backgrounds).

- Loading state as narrative moment: Use illustrated asset (paper plane, spinner graphic) + calming copy ('Saving your information...', 'Wait while we secure...') to reduce perceived wait time. Never silent or blank.
- Trust signals and social proof: User count ('350,000 kids!'), testimonials ('An easy way for me to save...'), security/privacy assurances (SSL badge, 'Terms & Conditions'), and achievement badges create confidence in age-gated or parental-sensitive flows.
- Skip/optional/not-now buttons for feature gates: Allow progression without completing every step. Widget installation, parental linking, and premium upsells show NOT NOW or SKIP variants. Respect user pace.
- Numeric input with phone-style keyboard: Age, PIN, and verification code entry use large number-pad keyboards with symbols (DEF, GHI, etc.) for easy thumb interaction. Avoid tiny spinners or text fields.
- Error feedback in familiar patterns: Red text, inline error messages, or toast notifications at bottom of screen. Never silent validation failures. Show remediation path ('Check for typos', 'Resend code').
- Celebration/success screen after key milestones: Profile complete, account verified, or first lesson started warrants visual/copy celebration ('Looking good!', 'All set!'). Encourages momentum and engagement.
- Two-lane visual system for parent vs. child content: Calm operational aesthetic (teal, sans-serif, list-based) for parent settings. Playful storybook aesthetic (vibrant, rounded, character-rich) for child-facing screens. Consistent branding but tonally distinct.

**Anti-patterns**
- Long-form signup on single screen: Do NOT ask name, email, password, age, character, and goals all on one page. Creates cognitive overload and high abandonment. Break into 3–5 sequential screens instead.
- Silent form validation: Red underlines without explanation. User doesn't know why field failed or how to fix. Always pair error state with copy ('Minimum 8 characters required').
- Disabled CTAs without explanation: Button is grayed out but user doesn't understand why. Always show adjacent tooltip or helper text ('Complete step 2 to unlock').
- Generic corporate/minimal aesthetic: Blue/gray corporate default, sans-serif, rectangular cards. Fails to signal 'kids education' to parent/child. Playful apps need color, character, and warmth.
- System permission prompts without context: iOS/Android system dialog pops with 'Microphone Access?' but no explanation why. User hits Don't Allow by default. Provide pre-dialog screen explaining benefit ('We need your mic for pronunciation feedback').
- No placeholder for empty/loading states: Screen goes blank during network request or renders empty list without explanation. Always show skeleton, spinner, or 'Loading...' copy with illustration.
- Uncontrolled branching paths: Conditional flows (Is this a parent or teacher? Does child exist already?) become spaghetti if not designed as clear tree. Use role/type selection early to lock user into single path.
- Hardcoded English or no i18n planning: Strings scattered in UI code instead of centralized bundle. Vietnamese, English, and other locales fail to render. Plan i18n from day one with key-based strings.
- No accessibility for reduced motion: Animations play regardless of user's accessibility preference (prefers-reduced-motion). Disable parallax, auto-scroll, or character animations for these users.
- Forgetting secondary lane (parent vs. child UX separation): Mixing operational (settings, parental controls, billing) with playful (lessons, rewards) confuses both audiences. Keep lanes visually/tonally separate even if same app.

- Dense Data Tables: Avoid HTML-style tables with many columns and rows—parents don't scan tabular data the same way they do stacked cards. Duolingo's badge grid and Finch's discovery feed outperform any spreadsheet view.

- Vague Progress ('On Track', 'Good Job') Without Numbers: Parents need specificity. 'Complete 10 quests (4/10 done)' is far better than 'Good progress this week.' Always pair qualitative feedback with a quantitative anchor.
- Aggressive Color or Urgency Language: Red warning states, flashing notifications, or 'MUST COMPLETE TODAY' pressure tactics trigger anxiety. Calm = muted backgrounds, soft accents, neutral language ('22 hours left', '3 days remaining').
- Inconsistent Icon Sets or Custom Emoji Soup: If you use colored circles, make them consistent (blue = discovery, green = completed, gray = pending). Mixing emoji styles from multiple sources feels unfinished and hard to learn.

- Hardcoded hex codes or colors not mapped to theme: All battery indicators use consistent green/yellow/red; don't invent new shades per field (breaks light/dark mode transitions).
- Missing device photo or icon: Text-only device identity (model code alone) is forgettable. IKEA, Fitbit, and Oura all use visual device representation.

- Progressive State Clarity: Every screen shows exactly one primary action. Sequence: (1) 'Start Setup' → (2) 'Searching...' (auto-animate) → (3) 'Device Found' (confirm) → (4) 'Connecting...' (spinner + estimated time) → (5) 'Connected ✓' (celebration + next step). No ambiguous states.
- Card-Based Device Discovery List: When multiple devices possible, render as scrollable cards (not text list). Ranked by signal strength (closest first).
- Celebration Feedback on Success: Confetti, brief animation loop, success sound, or haptic pulse. TJBot child lane: animated character reaction (robot jumps, eyes widen). Dwell on success screen for 1-2s before auto-advancing to next setup step.
- Contextual Help Text, Not Errors: Instead of 'Failed to connect', say 'Move closer to the robot and try again' or 'Make sure Bluetooth is ON in Settings'. Tie help to the current state and user's likely misconception. Use small secondary text (12px, 50% opacity) below the primary action.
- Visual Hierarchy via Density & Color: Primary action button largest & brightest (brand color). Secondary actions (Cancel) smaller and muted. Status text medium-weight, high contrast. Remove noise — limit each screen to 1 prompt + 1 progress indicator + 1 next-action button.
- Device Illustration or Icon Reinforcement: Show a simplified illustration of the robot/device on pairing screens. Updates based on pairing state: (searching = animated scanning rays), (found = device highlighted), (connecting = device + signal animation), (connected = device + checkmark). Reduces instruction text needed.
- No Buried Settings: Never require users to leave the pairing flow to toggle Bluetooth, WiFi, or permissions. Either: (a) request in-flow permission with native OS dialog, (b) explain why permission needed and guide user back, or (c) auto-enable if app has that capability (rare on iOS).
- Parent Lane: Calm Operational Language: For parent onboarding (Wispr-Flow side), use clear instructional tone: 'Your child's robot will now pair with the Wi-Fi.' Use secondary text for safety caveats ('Keep your robot within 10 feet during setup'). Avoid technical jargon (e.g., say 'Wi-Fi network' not 'SSID').
- Child Lane: Playful Micro-Interactions: For child-facing pairing, add personality — animated character states, celebratory sounds, sticker rewards. But keep interaction model simple: tapping once, watching feedback. Avoid multi-step instructions; let animation tell the story.
- Accessibility: Semantic State Labels: Use VoiceOver-friendly text: 'Device found' not just 'Found'. Status spinners must have aria-live='polite' or equivalent. Ensure color isn't the only signal (use text + icon). Focus order matches reading order. Test with Switch Control for single-tap navigation.
- Signal Strength as Trust Indicator: If Bluetooth/WiFi signal is weak, show icon (1-3 bars) and optional hint ('Move closer'). Strong signal = checkmark. This educates users on distance constraints and troubleshooting without errors.
- Timeout & Retry Pattern: If scanning takes >30s without finding device, show: 'No device found. Make sure your robot is powered on, then tap Retry.' Offer 'Check Setup Guide' link if retries fail 2x. Never hang indefinitely.
- No Modal Dialogs for Pairing: Use full-screen or sheet-based flows, not popovers. Modals feel like interruptions; pairing is the primary task. Sheet (for parent lane) or full-screen (for child lane) keeps focus on the setup.
- Skip or Back Button Placement: Place clearly but not prominent. Usually top-left or in footer. If user cancels, confirm: 'Pairing incomplete. Are you sure?' One-way trip to skip avoids accidental exits.
- Brand Color Saturation: Reserve the brightest primary color for the connect/confirm button. Use brand color sparingly elsewhere (icon tint, border accents). Majority of screen: white/light-gray background, neutral text. Prevents fatigue and keeps CTA paramount.

**Anti-patterns**
- Ambiguous spinner-only states without progress text: User sees spinning circle but doesn't know if pairing is working, stalled, or failed. Always pair spinner with: 'Connecting to TJBot...' and optionally a timeout estimate ('This usually takes 10-15 seconds').
- Burying the 'Try Again' button after failure: If pairing fails, the recovery action must be immediate and obvious. Don't require the user to navigate back to a menu. Show failure message + 'Try Again' button on the same screen.
- No visual affordance for scrollable device list: If multiple devices appear, users may miss the scroll hint (arrow icon, gradual reveal, or bouncy scroll). Test with first-time users — they often don't realize they can scroll.
- Dismissible success state without guardrails: If success screen auto-dismisses, ensure the next screen doesn't require pairing to have worked (e.g., don't load a device-control dashboard expecting the pairing to be cached). Verify state server-side.
- Modal notification for permission requests instead of inline prompt: 'Enable Bluetooth' as a pop-up modal is jarring. Use inline text in the pairing screen: 'Turn on Bluetooth to continue' with visual button to prompt the native OS dialog.
- Forced WiFi network entry when device advertises it: Some devices broadcast a temporary WiFi network during pairing. Don't force users to manually enter SSID/password if you can auto-detect and list the device's broadcast network. Detect and pre-populate.
- No distinction between 'scanning' and 'waiting for user action': If pairing requires the user to press a button on the device first, clearly state: 'Press the power button on your robot, then tap Pair.' Don't show a generic 'Scanning...' spinner when pairing is idle.
- Timeout errors that don't suggest next steps: 'Bluetooth connection timeout' is not actionable. Instead: 'TJBot didn't respond in time. Is it powered on? Move it closer and try again.'
- Ignoring accessibility: No color-blind safe palette (red/green status without icons), no haptic feedback alternative on silent mode, no text-to-speech for spinners. Particularly critical for children's apps (COPPA considerations and learning diversity).
- Over-animation that impedes progress: Pairing animation is motivational, but >1s of confetti or looping character reaction delays getting to the next step. Celebrate briefly (0.6-0.8s), then auto-advance.
- Asking for device name during pairing flow: If you need a device name, collect it after pairing succeeds, not during the connection attempt. Interrupting the pairing flow with form input reduces perceived success.
- Showing raw error codes or technical tokens: 'Error code 0x400B_PAIRING_REJECTED' is useless to a parent. Map to: 'The robot didn't recognize your request. Restart the robot and try again.'
