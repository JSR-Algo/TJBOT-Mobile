### Reading the contract correctly

The contract has two artifacts and neither alone answers "is this route served?":

| Artifact | Contains | Caveat |
|---|---|---|
| `openapi.json` → `paths` | Nest routes under the `/v1` global prefix | `generate-openapi.mjs` filters to `IN_SCOPE_TAGS` = auth, households, devices, notifications, admin, internal, lessons. A **served** route outside those tags is absent here. Absence means *undocumented*, never *unserved*. |
| `openapi.json` → `x-tbot-modular-route-contract.routes` | the modular Express runtime | Only the subset matched by `isBridgeRoute()` (`src/modules/app/modular-route-bridge.ts`) is actually mounted. The rest are **declared but unrouted**, so they 404 exactly like an undeclared route. |

Both traps produce false results if ignored: a first pass using `paths` alone
flagged 50 of 102 mobile calls as broken (wrong — most are served but untagged),
and a second pass that trusted the modular contract's declarations missed that
`POST /v1/children/{id}/archive` is declared yet never bridged. The final gate
scans the Nest `@Controller` decorators directly for "served" and mirrors
`isBridgeRoute()` for the modular half.

## Defects found and fixed

### 1. Ten mobile call sites addressed routes that can only 404 (HIGH)

Five had an exact contract equivalent under a different name — the mobile
behaviour was already written, only the URL was wrong:

| # | Mobile called | Backend serves | Reachable from |
|---|---|---|---|
| 1 | `GET /v1/orders/{id}` | `GET /v1/billing/orders/{id}` | `OrderConfirmScreen:31` (production) |
| 2 | `POST /v1/orders/{id}/cancel` | `POST /v1/billing/orders/{id}/cancel` | `SubscriptionsScreen:131` (production) |
| 3 | `POST /v1/orders/{id}/return` | `POST /v1/billing/orders/{id}/return-request` | exported, no caller |
| 4 | `POST /v1/billing/subscription/reactivate` | `POST /v1/billing/reactivate` | `SubscriptionsScreen:219` (production) |
| 5 | `POST /v1/children/{id}/archive` | `PATCH /v1/identity/children/{id}` `{status:'archived'}` | exported, no caller |

Row 5 is the subtle one: `POST /v1/children/:childProfileId/archive` **is** in the
modular route contract, so a declaration-only check calls it documented. But
`isBridgeRoute()` forwards only `/v1/billing/*`, the entitlements internal, the
Stripe webhook, and two notification routes — `/v1/children/*` is never mounted.
Archiving is a status transition on the ADR-0011 D1 route that `deleteChild`
already uses; any household parent may drive it and it is idempotent.

Five had no backend contract at all and now fail closed on the
`BACKEND_CONTRACT_UNAVAILABLE` sentinel instead of issuing a request that cannot
succeed: `getShippingStatus`, `activateRobot`, `refreshEntitlementsAfterPurchase`,
`getParentToday`, `getParentHistory`.

`POST /v1/device/activate` deserves a note — it exists, so a path-similarity check
would "fix" `activateRobot` onto it. It is the OTA device alias: it authenticates
by `device-id`/`client-id` headers and accepts no activation code, so it cannot
serve a consumer activation flow. Left uncontracted deliberately.

### 2. `mapOrder` read fields the orders module does not emit (HIGH)

`OrdersService.orderResponse` answers `{ data: { orderId, state, stateVersion } }`.
The mapper read `raw.id` and `raw.status`, so `Order.id` and `Order.status` were
`undefined` behind a `string`/union type — and `OrderConfirmScreen`'s
`next.status === 'paid'` gate could never fire, so the post-purchase entitlement
refresh never ran. This is a second, independent defect: fixing only the URL
(defect 1) would have left the screen silently wrong rather than obviously broken.

The two order vocabularies also differ. Backend `OrderState` is
`created | paid | fulfilling | shipped | arrived | activated | cancel_pending |
cancel_failed | cancelled | refunded`; mobile `Order['status']` is
`pending | confirmed | shipped | delivered | paid | pending_payment | cancelled |
refunded`. They overlap on four names. `mapOrderStatus` now translates explicitly
rather than casting, so an unmapped backend state cannot masquerade as a mobile
one; states mobile has no name for collapse to `pending`, which preserves the only
live consumer exactly. Widening the mobile union is purchase-feature work (F-T52-05).

### 3. Three copies of one error class (MED — deep-dive box 4)

`BackendContractUnavailableError` was declared independently in
`undocumented-api-routes.ts`, `parent.api.ts`, and `purchase.api.ts`. All three
carried `code: 'BACKEND_CONTRACT_UNAVAILABLE'`, so `code`-based handling worked,
but `instanceof` was **false** across module boundaries — three nominal types
behind one code. `parent.api.ts` and `purchase.api.ts` now re-export the canonical
class.

Separately, `parent.api.ts`'s `getSafetyConfig`, `updateSafetyConfig`,
`getSettings` and `updateSettings` rejected with a bare
`new Error('not implemented')`. That carries no `code`, so `normalizeError`
mapped it to `UNKNOWN_ERROR` — indistinguishable from a genuine server fault. All
four now use the typed sentinel.

### 4. `undocumented-api-routes.ts` justified nothing (the Done criterion)

The file held only the error class and helper. The 28 operations that threw
through it carried no record of *why*, so "documented in the backend contract or
removed/justified" could not be evaluated. It is now a typed registry —
**38 rows**, one per operation, each with `module`, `attemptedRoute`, `status`,
`reason`, and (where applicable) `owner`.

`status` is what stops the file rotting, and the gate enforces it in both
directions:

- `no-backend-contract` (29 rows) — the gate asserts the route really is absent.
  The day the backend ships one, the gate goes **red** and forces a revisit.
- `backend-route-exists` (9 rows) — the backend serves it, but wiring mobile is
  feature work; `owner` is mandatory and names the §5 row tracking it. The gate
  asserts the route is still present.

The nine `backend-route-exists` rows are honest debt, not silence: `createOrder`
(`POST /v1/billing/orders`), `controlsApi.get/updateControls` (`/v1/controls/{id}`),
the four `dashboard.ts` summaries (`/v1/summaries/*`), and `getFirmwareVersion` /
`runFirmwareUpdate` (`/v1/robots/{id}/ota*`). Each is routed below.

## What the new gate checks

`scripts/check-api-contract-sync.mjs` (replacing the placeholder) fails on:

1. a `client.<verb>(...)` route in `src/services/api/**` that nothing serves;
2. a `backendContractUnavailable(op)` with no registry row;
3. a registry row whose `status` no longer matches backend reality (both directions);
4. a `backend-route-exists` row with no `owner`;
5. an orphaned registry row (declared but never thrown).

It also self-checks: it aborts rather than passing vacuously if it scans zero
backend routes or zero mobile calls, and it fails if its mirror of
`isBridgeRoute()` drifts from the backend source. Served-but-undocumented routes
are reported as informational notes (24 today — see F-T52-08), not failures,
because `paths` is tag-filtered by design.
