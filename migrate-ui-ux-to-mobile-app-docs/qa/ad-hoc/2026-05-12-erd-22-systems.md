## Critique-before-close — 6 honesty questions (TBOT/CLAUDE.md Step 7)

**Q1. Root cause vs symptom — did we model the actual contract or just rename existing concepts?**
The ERD names a small number of plan-level normalisations (`users` vs `parent_accounts`, `children` vs `child_profiles`, `admin_commands` vs `admin_audit_log`, etc.) but every entity is sourced from the system spec's data-model section. Where the spec embeds state (e.g. `refresh_token_hash` inside `auth_sessions`) we lifted to a per-generation `refresh_tokens` table because replay detection requires an explicit row. **Decision tracked in the corresponding entity .md**. The polymorphic `audit_log.target_id` is a deliberate architectural decision documented in `audit_log.md` — not a rename.

**Q2. Code vs docs — does the implementation match the system specs read in Phase 2?**
Every entity .md cites the system spec section it's sourced from (Phase 2 lane reports list spec anchors). Plan §3 entity manifest specifies 95-115 tables; final tree has 101 entity tables + 1 template = 102 — within range.

**Q3. Test quality — is the validator meaningful or ceremonial?**
The validator enforces 7 FAIL rules + 5 WARN rules that catch real bugs (forgot-to-add-pk; cross-domain ref to nonexistent column; entity without sibling .md; etc.). `check-acceptance.mjs` verifies every AC explicitly with both shape and content checks. **Caveat**: the ERD is design-only — there are no executable code tests to run because there's no production code yet. The validator + checker IS the test suite. It locks behaviour: any change that breaks a frontmatter rule or introduces a serial PK fails the build.

**Q4. Drift status — any docs/task/scope drift unresolved?**
4 minor stale facts in `_global/` narrative noted in the reviewer findings (F-1..F-4 — Phase 5 cleanup invalidated some Phase 4 wording). None affect the entity files or the validator. Documented in `phase5-critique-findings.md` for next maintenance pass. **No critical drift.**
