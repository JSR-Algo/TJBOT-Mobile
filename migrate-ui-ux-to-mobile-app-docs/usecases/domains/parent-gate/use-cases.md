## UC-PR01 — Authenticate Parent

> **2026-05-12 P3.B:** This UC was rewritten when `docs/decisions/0005-parent-gate-security-model.md` was accepted. Pre-2026-05-12 body kept the original speed-bump description; current body documents the server-validated PIN model per ADR-0005 D1–D10. The pre-ADR prototype UI (`ParentGateScreen.tsx` random 3-digit) is retained as a development scaffold behind a build flag until P4 wiring completes.

- **Goal:** A parent proves they hold the household's parent role by entering a server-validated PIN. Issues a `parent_session` JWT (24h absolute, 15-min idle) that gates every `parent_*` surface and every sensitive write across the app. Required to ship for COPPA / GDPR / commerce / child-safety compliance.
- **Trigger:** Any UC that has `[requires] parent-gate : UC_PG_PASS` in its puml notes (UC-H08, UC-CL01, UC-PR02, UC-DP01, UC-RM01) navigates to `parent_gate`. Also triggered when an existing `parent_session.idle_until` has lapsed during navigation. Sensitive actions (purchase, controls-update, sub-cancel, child-profile delete, safety override, account delete) require a JWT minted within the last 60s and re-trigger this UC on stale.
- **Preconditions:** User is on `parent_gate`; auth status is `authenticated`; `parent_pins.bcrypt_hash` row exists for `user_id`; `parent_lockouts.locked_until` is in the past (or NULL).
- **Main Flow:**
  1. `ParentGateScreen` mounts; renders the 4-digit numeric keypad input (replacing the random-3-digit prototype).
  2. Parent enters PIN; tap "Confirm".
  3. ParentApp POSTs `/v1/parent/auth` with `{user_id, pin, X-Request-Id}` per sequence `docs/sequences/07-parent/parent-gate-validate.sequence.mmd`.
  4. Server runs ADR-0005 D3 4-step order: (a) Redis token-bucket per `(user_id, ip_hash)` 10/5min — 429 *without* writing an attempt row; (b) `parent_lockouts.locked_until > now()` precheck → 423; (c) bcrypt compare against `parent_pins.bcrypt_hash`; (d) outcome insert into `parent_auth_attempts`.
  5. On success: server issues `parent_session` JWT with `jti`, `idle_until=now()+15min`, `expires_at=now()+24h`; row written to `parent_sessions`.
  6. ParentApp stores JWT in `parent.store`; navigates to the original target screen (`parent_summary` for the default, or the specific parent surface that triggered the gate).
- **Postconditions:** ParentApproval FSM (`.omc/plans/state-machines-mobile-ux.md` §2.4) transitions LOCKED → AUTHENTICATED → VIEWING_DASHBOARD. JWT cookie/header used by every subsequent protected request. Lockout counter reset on success.
- **Alt Flow:**
  1. Parent taps "Back to play" → returns to `home_hub_idle`; no row written. FSM stays at LOCKED.
  2. JWT already valid (idle_until > now()) — `parent_gate` short-circuits client-side; no server call.
  3. JWT idle-expired but absolute-unexpired — re-prompt for PIN; same flow but suppresses the lockout precheck row insert if successful within the same minute (avoids duplicate audit rows on idle-bounce).
- **Error Flow:**
  1. `pin_incorrect` → server returns 401; ParentApproval FSM GATE_PROMPT → GATE_RETRY; client shows "Wrong PIN"; attempt counter increments.
  2. Attempt 5 → server transitions to GATE_LOCKED_OUT; `parent_lockouts.locked_until = now() + 15min`; client shows "Locked for 15 minutes" screen (routes to `parent_locked_out` per audit fix; P3.B wiring).
  3. `rate_limited` (10 attempts in 5 min) → 429 with `Retry-After`; client shows backoff toast; no attempt row written (audit C6).
  4. `account_locked_out` (active lockout window) → 423; client shows lockout countdown; PIN field disabled.
  5. Primary-parent unlock path: separate UC where primary parent invokes `POST /v1/parent/lockout/clear`; covered in sequence + P5 follow-up UC.
