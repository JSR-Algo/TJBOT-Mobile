## UC-PR02 — View Parent Summary

- **Goal:** Parent sees a consolidated dashboard of their child's recent learning activity, providing a one-stop overview before drilling into details.
- **Trigger:** Parent completes parent-gate (UC-PR01) and lands on `parent_summary`; or taps "Parent summary" from any surface that passes the gate.
- **Preconditions:** Passed parent-gate (UC-PR01) within current session (KD4 — speed-bump, not RBAC). `getParentSummary()` API is reachable.
- **Main Flow:**
  1. `ParentSummaryPage` mounts and calls `getParentSummary()` from `src/services/api/parent.api.js`.
  2. UI renders today's stats card, 30-day streak indicator, and quick-links to UC-PR03, UC-PR04, UC-PR05.
  3. Settings icon in header links to UC-PR06.
  4. Parent can tap any card to drill into the respective sub-UC.
- **Postconditions:** Summary displayed; no state mutations. Navigation state is `parent_summary`.

## UC-PR05 — View Safety & Privacy

- **Goal:** Parent reviews the safety and privacy settings governing their child's robot interactions, and understands what data is collected.
- **Trigger:** Parent taps "Safety & Privacy" from UC-PR02 (`ParentSummaryPage`).
- **Preconditions:** Passed parent-gate (UC-PR01) within current session. `getSafetyConfig()` API is reachable.
- **Main Flow:**
  1. `ParentSafetyPage` mounts and calls `getSafetyConfig()` from `src/services/api/parent.api.js`.

  5. Back navigation returns to UC-PR02.

## UC-PR06 — Configure Parent Settings

- **Goal:** Parent adjusts parent-controlled settings (language, child profile, privacy/account controls, and AI voice consent) from the `parent_settings` screen.
- **Trigger:** Parent taps the settings icon in the `ParentSummaryPage` header (puml note: `[header]` from UC-PR02).
- **Preconditions:** Passed parent-gate (UC-PR01) within current session.
- **Main Flow:**
  1. `ParentSettingsPage` mounts in the parent flow as state `parent_settings`.
  2. UI renders language, child profile, personality filters, privacy/account controls, and the AI voice lesson consent section.
  3. Parent taps "Allow voice lessons"; app records active AI voice consent through `recordAiVoiceConsent()`.
  4. Parent taps "Pause voice lessons"; app withdraws active AI voice consent through `withdrawAiVoiceConsent()`.
  5. Save success or failure is shown inline on `parent_settings`; the flow does not navigate to a separate voice setup screen.
  6. Back navigation returns to UC-PR02.
- **Postconditions:** Parent setting changes are persisted when the backing API succeeds; voice consent remains parent-controlled inside `parent_settings`.

## UC-PR08 — Enable Biometric Unlock

- **Goal:** Parent opts in to FaceID / BiometricPrompt to satisfy the ADR-0005 D6 60-second freshness gate without re-typing the PIN every time. Per ADR-0009.
- **Trigger:** Tap "Biometric unlock" toggle in `parent_settings → Safety & Privacy`.
- **Preconditions:** Authenticated parent with valid `parent_session`; device has biometric enrolled; freshness JWT < 60s (re-PIN if stale before opt-in).
- **Main Flow:**
  1. Toggle ON triggers `BiometricSetupScreen`.
  2. OS biometric prompt → on success, system writes the `parent_session` JWT into OS Keychain with `BIOMETRY_CURRENT_SET` accessControl.
  3. Client stores `biometric_enrollment_id` (a derived hash) alongside.
  4. Server toggles `parent_sessions.biometric_enabled=true` for that jti.
  5. Subsequent sensitive actions (purchase, controls update, sub-cancel, etc.) check `isJwtFresh()` first → if stale but `hasValidSession()`, prompt biometric → server re-stamps `issued_at` via `POST /v1/parent/session/refresh-freshness`.
- **Postconditions:** Biometric cache active. Until next biometric enrollment change or 24h `expires_at` elapses, parent skips PIN entry for sensitive actions.
- **Alt Flow:**
  1. Toggle OFF: client clears Keychain entry + server flips `biometric_enabled=false`. PIN entry required for every sensitive action going forward.
  2. New biometric enrollment added (parent adds a 2nd fingerprint) → next biometric unlock fails → falls back to PIN per ADR-0009 D6.
- **Error Flow:**
  1. Biometric refresh rate-limited (30/24h per jti) → 429; client surfaces "Try the PIN this time" toast.
  2. Biometric prompt cancelled by user → no state change; falls back to PIN screen.
  3. JWT absolute expiry passed → biometric unlock cannot extend; user must full re-PIN.
- **Related:** ADR-0009. Sequence `07-parent/freshness-refresh.sequence.mmd`. Parent_session JWT shape.

## UC-PR09 — Invite Secondary Parent

- **Goal:** Primary parent adds another adult to the household (co-parent, grandparent, nanny). Per ADR-0010 D3.
- **Trigger:** Tap "Invite parent" in `ParentFamilyScreen`.
- **Preconditions:** Authenticated parent with `role='owner'` (per existing `household_members` table); fresh parent JWT < 60s.
- **Main Flow:**
  1. Primary enters email + optional nickname.
  2. ParentApp POSTs `/v1/household/parents/invite` with `{email, nickname, X-Request-Id}`.
  3. Server creates `household_members` row (status=`pending_invite`, role=`manager`, invited_by_user_id=primary's user_id).
  4. SES sends `tbot://household/accept?token=…` magic link.
  5. Invitee taps link → if they have an account, accept → `household_members.status='active'`; if new user, full signup-then-accept flow.
- **Postconditions:** Secondary parent active in household; can perform day-to-day actions (ADR-0010 D6).
- **Alt Flow:**
  1. Invitee already in another household → server 409; offer to leave existing first (UC-PR12).
  2. Invitee already in THIS household → 409 with `already_household_member`.
- **Error Flow:**
  1. Non-primary attempts → 403 `requires_role=primary`; UI explainer.
  2. Invite expires after 7 days unused; primary can re-invite.
- **Related:** ADR-0010 D3. Sequence `07-parent/household-invite-parent.sequence.mmd`.

## UC-PR10 — Revoke Secondary Parent

- **Goal:** Primary parent removes a secondary parent from the household. Per ADR-0010 D5 (primary-only).
- **Trigger:** Tap "Remove" on secondary's row in `ParentFamilyScreen`.
- **Preconditions:** Authenticated primary with fresh JWT; target user is a secondary (role=`manager`) in this household.
- **Main Flow:**
  1. Confirm sheet "Remove <name> from household? They'll lose access immediately."
  2. ParentApp DELETEs `/v1/household/parents/{user_id}`.
  3. Server sets `household_members.status='revoked'`, `revoked_at=now()`.
  4. Server revokes all `parent_sessions` for the removed user.
  5. SES emails both the removed parent ("You've been removed from <household>") and the primary ("Removed <name>").
- **Postconditions:** Secondary loses access. Their child-profile creates are retained but they cannot edit them.
- **Alt Flow:**
  1. Primary attempts to revoke self → 403 with `revoke_self_forbidden`; must transfer primary first (UC-PR11) or delete account (UC-A12).
- **Error Flow:**
  1. Already revoked → 200 idempotent.
- **Related:** ADR-0010 D5 + audit trail (D9).

## UC-PR11 — Transfer Primary

- **Goal:** Move the `primary` role to an existing secondary parent. Per ADR-0010 D7. 2-step 7-day async flow.
- **Trigger:** Tap "Make primary" on secondary's row in `ParentFamilyScreen`.
- **Preconditions:** Authenticated primary; target is an active secondary in household; no in-flight transfer.
- **Main Flow:**
  1. Heavy confirm "Make <name> the primary parent? They'll take over payment + ownership decisions. You'll become a secondary."
  2. ParentApp POSTs `/v1/household/transfer-primary` with `{to_user_id}`.
  3. Server creates `primary_transfer_requests` row state=`requested`; SES emails target.
  4. Target's ParentApp shows in-app banner + email link.
  5. Target taps "Accept primary role" → fresh biometric+PIN check (ADR-0009 freshness) → POST `/v1/household/transfer-primary/confirm`.
  6. Server flips both `household_members.role` rows in same txn; revokes prior primary's parent_sessions; SES emails both.
- **Postconditions:** Roles swapped. Prior primary becomes secondary; new primary owns subscription, payment, account-delete.
- **Alt Flow:**
  1. Target declines → server marks `state='cancelled'`; no change.
  2. 7 days pass without confirm → auto-`expired`; primary can re-initiate.
- **Error Flow:**
  1. Target not in household → 404.
  2. Target is already primary → 409.
  3. In-flight transfer exists → 409; must cancel first.
- **Related:** ADR-0010 D7. Sequence `07-parent/household-transfer-primary.sequence.mmd`.

## UC-PR12 — Leave Household

- **Goal:** Secondary parent voluntarily exits a household. Per ADR-0010 D8.
- **Trigger:** Tap "Leave household" in `ParentFamilyScreen → your row`.
- **Preconditions:** Authenticated parent with `role='manager'` (secondary); fresh parent JWT < 60s.
- **Main Flow:**
  1. Confirm sheet "Leave <household_name>? You'll lose access to its children + lessons."
  2. ParentApp POSTs `/v1/household/leave`.
  3. Server sets `household_members.status='revoked'`, `revoked_at=now()`; revokes all parent_sessions.
  4. Client clears local household state; routes to `LoginScreen` (user can join another household via invite OR start their own).
- **Postconditions:** User no longer in household. Their `users` row preserved (can be re-invited).
- **Error Flow:**
  1. User is primary → 409 `cannot_leave_as_primary`; must transfer primary first (UC-PR11) or delete account (UC-A12).
  2. User is last member → 409 `last_member_cannot_leave`; must delete household via account-delete.
- **Related:** ADR-0010 D8. Sequence `07-parent/household-leave.sequence.mmd`.
