## UC-BU01 — View Robot Overview

- **Goal:** Parent gets a high-level introduction to the TBOT robot product, building purchase intent before exploring details.
- **Trigger:** Parent taps "Buy TBOT" / "Get started" CTA from `home_hub_idle` or the marketing entry point.
- **Preconditions:** Parent is authenticated; app is connected.
- **Main Flow:**
  1. `RobotOverviewPage` mounts and renders static hero content (product image, headline, key selling points).
  2. "How it works" CTA navigates to UC-BU02.
  3. "Buy now" skip CTA can jump directly to UC-BU04 (bundle selection).
- **Postconditions:** Parent is on the discovery funnel entry screen; no state mutations.

## UC-BU02 — View How It Works

- **Goal:** Parent understands the product's learning methodology and interaction model before committing to purchase.

- **Main Flow:**

  3. "What's included" CTA navigates to UC-BU03.
- **Postconditions:** Parent has seen the methodology overview; no state mutations.

## UC-BU04 — Pick Bundle

## UC-BU07 — Place Order / Checkout

- **Goal:** Parent confirms the order summary and initiates the checkout, which creates the order record and presents payment options.
- **Trigger:** Parent taps "Proceed to checkout" from UC-BU06. Puml edge: `UC_BUY_PRIV ..> UC_BUY_CHECKOUT`.
- **Preconditions:** Bundle, subscription, and privacy consent are confirmed; `usePurchaseStore.paymentStatus === 'idle'`.
- **Main Flow:**
  1. `CheckoutPage` mounts and renders order summary (bundle, subscription, price total).
  2. Page calls `createOrder()` from `src/services/api/purchase.api.js` with an idempotency key (`http/idempotency.js` — puml note).
  3. On success, `usePurchaseStore.startCheckout(orderId)` is called; payment options appear.
  4. Parent chooses Apple Pay (UC-BU08) or Card (UC-BU09) via extend flows.
- **Postconditions:** Order is created server-side; `usePurchaseStore.orderId` is set; `paymentStatus` is `'pending'`.
- **Alt Flow:**
  1. `createOrder` returns an error → show order-creation failure with retry CTA; `paymentStatus` stays `'idle'`.

## UC-BU08 — Pay with Apple Pay

- **Goal:** Parent completes payment via Apple Pay, delegating the transaction to the Apple Pay provider.
- **Trigger:** Parent taps "Apple Pay" payment option on `CheckoutPage`. Puml edge: `UC_BUY_CHECKOUT ..> UC_BUY_APPLE` (extend).
- **Preconditions:** Order is created (`usePurchaseStore.orderId` non-null); Apple Pay is available on device; payment provider identity NOT CONFIRMED IN SOURCE (KD9 — all backend cells sentinel).
- **Main Flow:**
  1. App triggers the Apple Pay payment sheet via the platform API.
  2. Parent authorises payment via Face ID / Touch ID.
  3. On provider success, app calls `processPayment()` from `src/services/api/purchase.api.js` to record the result.
  4. `usePurchaseStore.confirmPayment()` is called; navigation advances to UC-BU10.
- **Postconditions:** Payment confirmed; `usePurchaseStore.paymentStatus === 'confirmed'`; navigates to order confirmation.
- **Alt Flow:**
  1. Parent cancels Apple Pay sheet → returns to `CheckoutPage`; `paymentStatus` stays `'pending'`.
  2. Payment declined → show decline message with retry and card-pay fallback options.

## UC-BU09 — Pay with Card

- **Goal:** Parent completes payment by entering card details, delegating the transaction to the payment provider.
- **Trigger:** Parent taps "Pay with card" payment option on `CheckoutPage`. Puml edge: `UC_BUY_CHECKOUT ..> UC_BUY_CARD` (extend).
- **Preconditions:** Order is created (`usePurchaseStore.orderId` non-null); payment provider identity NOT CONFIRMED IN SOURCE (KD9 — all backend cells sentinel).
- **Main Flow:**
  1. `CardPayPage` or in-checkout card form mounts and renders card number, expiry, and CVV fields.
  2. Parent enters card details; client-side validation runs on blur.
  3. On "Pay" tap, app calls `processPayment()` from `src/services/api/purchase.api.js`.
  4. `usePurchaseStore.confirmPayment()` is called on success; navigation advances to UC-BU10.
- **Postconditions:** Payment confirmed; `usePurchaseStore.paymentStatus === 'confirmed'`; navigates to order confirmation.
- **Alt Flow:**
  1. Card declined → show decline message with re-entry affordance; `paymentStatus` stays `'pending'`.
  2. Validation failure → inline field errors; submit blocked until corrected.

## UC-BU11 — Track Shipping

- **Goal:** Parent monitors the delivery status of their TBOT robot after order is placed.
- **Trigger:** Parent taps "Track my order" from UC-BU10, or re-enters the purchase domain after order is placed. Puml edge: `UC_BUY_CONFIRM ..> UC_BUY_SHIP`.
- **Preconditions:** `usePurchaseStore.orderId` is set; `getShippingStatus()` API is reachable.
- **Main Flow:**

  4. When status is `'delivered'`, a "My robot arrived!" CTA appears → UC-BU12.
- **Postconditions:** Shipping status displayed and stored in `usePurchaseStore.shippingStatus`.

## UC-BU13 — Activate Robot with Code

- **Goal:** Parent pairs the physical robot with their account by entering the activation code printed on the device, delegating confirmation to the robot device actor.
- **Trigger:** Parent taps "Start setup" from UC-BU12. Puml edge: `UC_BUY_ARRIVED ..> UC_BUY_ACTIVATE`.
- **Preconditions:** Robot is powered on; parent has the printed activation code. `activateRobot()` API is reachable.
- **Main Flow:**
  1. `ActivateRobotPage` mounts with an input field for the activation code.
  2. Parent enters the code (format: alphanumeric, 6–8 characters).
  3. On "Activate" tap, app calls `activateRobot()` from `src/services/api/purchase.api.js` with the code.
  4. `activateRobot()` delegates to Robot actor (puml: `UC_BUY_ACTIVATE ..> Robot : <<delegate>> (activation code)`).
  5. On success, navigation advances to UC-BU14.
- **Postconditions:** Robot is linked to the parent's account; activation state is persisted server-side.
- **Alt Flow:**
  1. Invalid or already-used code → inline error message; retry allowed.
  2. Robot not reachable / timeout → error with troubleshooting steps.

## UC-BU15 — Cancel Order (pre-shipment)

- **Goal:** Parent cancels an order that has not yet shipped, releasing the Stripe authorisation and any inventory hold.
- **Trigger:** Tap "Cancel order" in order-history row; requires fresh parent JWT < 60s per ADR-0005 D6.
- **Preconditions:** `orders.state ∈ { CREATED, PAID, FULFILLING }` (per Order SM §2.6). Once SHIPPED, treat as return (UC-BU16) instead.
- **Main Flow:**
  1. ParentApp POSTs `/v1/billing/orders/{order_id}/cancel`.
  2. BillingService transitions `orders.state → CANCELLED` (CAS on state_version); calls Stripe to void or refund the payment intent; emits `order.cancelled` event.
  3. Email confirmation via SES; order-history row updates.
- **Postconditions:** Order CANCELLED terminal; Stripe charge voided or refunded; inventory hold released.
- **Error Flow:**
  1. `already_shipped` 409 → suggest UC-BU16 return flow.
  2. `stripe_unavailable` 503 → 202 accepted with `cancellation_pending`; backoff retry.
- **Related:** Order SM §2.6. Sequence TBD (P5 follow-up).

## UC-BU16 — Request Refund / Return

- **Goal:** Parent requests a refund/return for a shipped or arrived order; admin-mediated approval flow.
- **Trigger:** Tap "Request return" in order-history row within 30-day return window.
- **Preconditions:** `orders.state ∈ { SHIPPED, ARRIVED, ACTIVATED }`; within `orders.arrived_at + interval '30 days'`.
- **Main Flow:**
  1. ParentApp POSTs `/v1/billing/orders/{order_id}/return-request` with reason code + freeform note.
  2. Server creates `refund_requests` row state=`pending_admin_review`; emails support queue (sys-12).
  3. Admin approves (out-of-app flow). On approval, Stripe processes refund; `orders.state → REFUNDED`.
  4. Parent receives status push notification via UC-MOBILE01.
- **Postconditions:** `refund_requests` row created; order transitions to REFUNDED on admin approval; SES email confirmation.
- **Alt Flow:**
  1. Lost-in-transit auto-refund: `tracking_number` shows "delivery exception" for 14+ days → CRON sweeper creates `refund_requests` row with reason=`carrier_lost`, auto-approved.
- **Related:** Order SM §2.6 REFUNDED transitions. Sequence TBD (P5 follow-up).

## UC-BU17 — Retry Payment (failed Stripe charge)

- **Goal:** Parent updates payment method after a charge failure and resumes their subscription (re-enters from past_due state).
- **Trigger:** Push notification or in-app banner from UC-SUB05 dunning flow.
- **Preconditions:** `subscriptions.state = PAST_DUE` per Subscription SM §2.7; parent JWT.
- **Main Flow:**
  1. ParentApp opens `pr_payment_update` (or in-context modal) and POSTs `/v1/billing/payment-method/update`.
  2. BillingService returns a Stripe SetupIntent; client presents Stripe SDK card sheet.
  3. On successful confirmation, BillingService retries the failed invoice charge.
  4. On charge success: `subscriptions.state → ACTIVE`; entitlements remain (PAST_DUE preserved them).
- **Postconditions:** Subscription ACTIVE; new payment method on file; failed invoice settled.
- **Error Flow:**
  1. Card declined again → return to step 2 with error toast; allow retry.
  2. Grace expired before retry → 410 with `Retry-After-Reactivation`; parent must re-subscribe (UC-SUB04 not eligible).
- **Related:** Sequence `docs/sequences/19-billing/dunning-past-due.sequence.mmd` (mobile re-entry path).

## UC-SUB01 — View Subscription Status

- **Goal:** Parent inspects current subscription state, period end, plan tier, and payment method.
- **Trigger:** Tap "Subscription" row in `parent_settings`.

- **Main Flow:**

## UC-SUB02 — Cancel Subscription

- **Goal:** Parent schedules subscription cancellation. Service continues until `current_period_end`.
- **Trigger:** Tap "Cancel subscription" in UC-SUB01 view; requires fresh parent JWT < 60s.
- **Preconditions:** `subscriptions.state ∈ { TRIAL, ACTIVE, PAUSED, PAST_DUE }`.
- **Main Flow:**
  1. Confirm sheet with "You'll keep access until <period_end>."
  2. POST `/v1/billing/subscription/cancel`. BillingService transitions `subscriptions.state → CANCELLED`, writes Stripe `cancel_at_period_end=true`.
  3. SES confirmation email; `audit_logs` row recorded.
- **Postconditions:** CANCELLED state; entitlements preserved until period end; auto-transition to EXPIRED + entitlement soft-revoke at period end.
- **Alt Flow:**
  1. Cancel-immediately variant (rare, GDPR right): same call with `effective: 'immediate'`; entitlements revoke now; Stripe refunds pro-rata.
- **Error Flow:**
  1. `already_cancelled` 409 idempotent.
  2. `cancellation_window_closed` 410 — should not happen given valid state precondition.
- **Related:** Subscription SM §2.7. Sequence `docs/sequences/19-billing/subscription-lifecycle.sequence.mmd`.

## UC-SUB03 — Pause Subscription

- **Goal:** Parent pauses subscription for up to 90 days (one pause per billing cycle).
- **Trigger:** Tap "Pause" in UC-SUB01 view; requires fresh parent JWT < 60s.
- **Preconditions:** `subscriptions.state = ACTIVE`; no `paused_this_cycle` flag set.
- **Main Flow:**
  1. ParentApp POSTs `/v1/billing/subscription/pause` with optional `resume_on YYYY-MM-DD` (max 90d out).
  2. BillingService transitions `subscriptions.state → PAUSED`; writes `paused_at`, `pause_resume_due`; updates Stripe.
- **Postconditions:** PAUSED state; entitlements still active (kid can still play during pause); billing skipped.
- **Error Flow:**
  1. `pause_already_used_this_cycle` 409 → toast "Already paused once this cycle; you can resume or cancel".
- **Related:** Subscription SM §2.7.

## UC-SUB04 — Resume Subscription

- **Goal:** Parent resumes a paused subscription, returning to active billing.
- **Trigger:** Tap "Resume" in UC-SUB01 view when state=PAUSED; OR automatic on `pause_resume_due` reaching now.
- **Preconditions:** `subscriptions.state = PAUSED`.
- **Main Flow:**
  1. POST `/v1/billing/subscription/resume`. BillingService transitions `subscriptions.state → ACTIVE`; clears `paused_at` / `pause_resume_due`; resumes Stripe billing.
- **Postconditions:** ACTIVE state; next charge on next normal cycle.
- **Related:** Subscription SM §2.7.

## UC-SUB05 — Handle Renewal Failure

- **Goal:** Parent receives notification of failed renewal and resolves it before grace expires.
- **Trigger:** Stripe webhook `invoice.payment_failed` → server transitions `subscriptions.state → PAST_DUE` → SES email + FCM push to parent.
- **Preconditions:** `subscriptions.state` transitioned to PAST_DUE.
- **Main Flow:**
  1. Parent taps notification → deep-link via UC-MOBILE01 → `pr_payment_update` screen.
  2. Parent updates payment method (UC-BU17). BillingService retries charge.
  3. Success → subscription ACTIVE; failure → continue dunning sequence.
- **Postconditions:** ACTIVE on success; CANCELLED at day-7 grace expiry on persistent failure.
- **Related:** Sequence `docs/sequences/19-billing/dunning-past-due.sequence.mmd`.
