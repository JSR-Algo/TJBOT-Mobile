## UC-RM01 — View My Robot

- **Goal:** Parent reviews every owned robot's authoritative reward identity and controls each robot's public leaderboard privacy.
- **Trigger:** Parent taps "My Robot" from `parent_settings`, landing on `rm_my_robot` (`MyRobotPage`).
- **Preconditions:** Parent passed UC-PR01; the authenticated household scope is available.
- **Main Flow:**
  1. `MyRobotScreen` reads the weekly leaderboard response and renders every `ownedRows` robot, including opted-out private rows.
  2. Each card shows only backend-returned child, robot, XP, lesson count, streak state, masked email, and visibility; missing device telemetry is not guessed.
  3. Each card exposes an independently focusable switch that writes the preference for that exact device ID. The non-interactive summary header carries the screen-reader summary so it cannot swallow the switch.
  4. Neutral actions open the server-backed detailed-status route and parent-confirmed factory-reset flow without claiming battery, Wi-Fi, courses, microphone, care, firmware, or support state on this hub.
- **Postconditions:** Every owned robot retains private rewards while its public preference reflects the latest server-confirmed mutation.
- **Alt Flow:**
  1. Loading, error/retry, and empty-owned-robot states remain explicit and translated.
  2. Parent taps back → returns to the parent summary.

## UC-RM02 — View Robot Status

- **Goal:** Parent reviews only the robot identity and operational state returned by the authenticated household device contract.
- **Trigger:** Parent navigates to `rm_status` from UC-RM01.
- **Preconditions:** Parent passed UC-PR01; an active child is selected.
- **Main Flow:**
  1. `RobotStatusScreen` resolves the selected child's robot through `GET /devices/household/me`.
  2. The page renders the backend-returned robot name, optional serial number, and online/offline state; an absent operational signal remains unavailable.
  3. Battery, Wi-Fi, courses, microphone, temperature, uptime, and software remain explicitly unavailable because this contract cannot represent them reliably.
- **Postconditions:** Parent has an authoritative identity/operational-state snapshot without prototype telemetry.
- **Alt Flow:**
  1. Loading, error/retry, offline, and no-matching-robot states remain explicit and translated.

- **Preconditions:** Parent passed UC-PR01; Robot is paired.
- **Main Flow:**
  1. `RobotWifiPage` renders the current SSID + signal card (`RobotWifiScreen.jsx:9` `DvShell title="Wi-Fi"`).

## UC-RM10 — Factory Reset

- **Goal:** Parent erases Robot back to factory state — destructive, gated, multi-step.
- **Trigger:** Parent navigates to `rm_factory_reset` (`FactoryResetPage`) from a settings deep link.
- **Preconditions:** Parent passed UC-PR01; Robot is paired.
- **Main Flow:**
  1. `FactoryResetPage` mounts in `step='warning'` (`FactoryResetScreen.jsx:11`).
  2. Parent reads the destructive-action warning; taps "Continue" → step transitions to `gate` (re-asks parent gate inline — `FactoryResetScreen.jsx:64`).
  3. Parent passes the inline gate; step transitions to `confirm` — last-check screen (`FactoryResetScreen.jsx:102`).
  4. Parent taps "Yes, erase Robot" → factory reset is invoked via `robot-mgmt.api.js → factoryReset` (cross-domain destructive delegate to Robot — see cross-domain-edges.json: UC-RM10→ACTOR:Robot); navigation returns to `rm_my_robot` (`FactoryResetScreen.jsx:119`).
- **Postconditions:** Robot is being erased; pairing state will require re-running UC-DP04 onward.
- **Alt Flow:**
  1. Parent taps "Try smaller fixes first" → routes to `rm_offline_help` (UC-RM11) — `FactoryResetScreen.jsx:46`.

## UC-RM11 — View Offline Help

- **Goal:** Parent reads a curated checklist of offline-recovery steps before escalating to support or factory reset.
- **Trigger:** Parent taps "Offline help" on UC-RM01 (or arrives from UC-RM10's "Try smaller fixes first"), landing on `rm_offline_help` (`OfflineHelpPage`).
- **Preconditions:** Parent passed UC-PR01; Robot is paired but reporting issues.
- **Main Flow:**
  1. `OfflineHelpPage` renders `DvShell title="Robot offline help"` (`OfflineHelpScreen.jsx:11`) with a list of remediation steps.
  2. Parent reads/applies a step; some steps offer a CTA that routes to a sub-screen (`OfflineHelpScreen.jsx:37`).
  3. Parent taps "Try connecting again" → returns to `rm_my_robot` (`OfflineHelpScreen.jsx:44`).
- **Postconditions:** Parent applied recovery steps; may have escalated to support.
- **Alt Flow:**
  1. Parent taps "Still stuck · contact support" → routes to `rm_support` (UC-RM12) — `OfflineHelpScreen.jsx:45`.

## UC-RM12 — Contact Support

- **Goal:** Parent submits a support ticket / message scoped to a topic (hardware / app / etc.).
- **Trigger:** Parent navigates to `rm_support` (`SupportPage`) from UC-RM11 escalation, UC-RM09 muffled-speaker fallback, or a "Contact support" link.
- **Preconditions:** Parent passed UC-PR01.
- **Main Flow:**
  1. `SupportPage` renders `DvShell title="Contact support"` (`SupportScreen.jsx:18`) with a topic picker (`SupportScreen.jsx:8-10`).
  2. Parent picks a topic, fills the message body.
  3. Parent taps "Send to support" → returns to `rm_my_robot` (`SupportScreen.jsx:74`).
- **Postconditions:** Support message is queued; Parent returned to hub.
- **Alt Flow:**
  1. Parent taps "Cancel" → returns to `rm_my_robot` without sending (`SupportScreen.jsx:75`).
